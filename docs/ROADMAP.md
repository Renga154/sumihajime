# ロードマップ（2026-09-22 起点）

都知事杯オープンデータ・ハッカソン2026はFinal Stageに進めなかった。ここからは
**通常のWebサービスとして展開する**。順序は次のとおり（2026-09-22 ユーザー決裁）。

1. 個人運営のまま品質を上げて使われ続ける状態にする
2. 23区から都内62、その先へ広げる
3. 収益化
4. 自治体やシビックテックへの移管

**1と2を同時に進め、その実績で3へ、3で得た関係を足がかりに4へ。**

---

## Phase A: 運用の土台と都内拡大（いま〜）

### A-1 通常運用に耐える土台 — 拡大より先にやる

ハッカソン向けには十分でも、常時公開のサービスとして欠けているものが5つある
（2026-09-22 実測）。利用者が増えるほど、これらが無い状態は痛くなる。

| #   | 欠けているもの                         | なぜ必要か                                                                                                                                                                                                                                                  | 規模 |
| --- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| 1   | **差分検知の定期実行と自動降格**       | 提出フォーム1-9に「運用ループを実装済み」と書いたが、実態はハッシュ計算と台帳という部品があるだけで、定期再取得も「要確認」への自動降格も繋がっていない。放置すると最終確認日が黙って古くなり、このサービスの中核の約束（最終確認日つきの公式根拠）が崩れる | 中   |
| 2   | 誤り報告・問い合わせの導線             | 正確さを売るサービスに、誤りを報告する窓口が無い。自治体からの連絡先にもなる                                                                                                                                                                                | 小   |
| 3   | 利用規約・プライバシーポリシーのページ | 免責は各ページにあるが、独立したポリシーページが無い。公開サービスの最低限                                                                                                                                                                                  | 小   |
| 4   | 死活監視                               | `/api/health` はあるが誰も見ていない。落ちても気づけない                                                                                                                                                                                                    | 小   |
| 5   | ライセンスの決定                       | A-3（OSS化）の前提。コード（MIT等）とデータ（出典側の規約に従う）を分ける必要がある                                                                                                                                                                         | 判断 |

1が最重要。他は小さいが、公開サービスとして無いのは恥ずかしい類のもの。

- 2026-09-22: **1 を実装**（ADR-014。Worker の毎時 Cron が承認済みソースを10件ずつ再取得し、更新日の変化・不達を `source_drift` に記録。該当手続きは読み出し時に「再確認中」へ自動降格、復帰は人手の再監査のみ。運用手順は `docs/ops/drift-check.md`）。

- 2026-09-23: **3・5 を実装**。`/terms`（利用規約）と `/privacy`（プライバシーポリシー）を全ページの
  フッターから到達できる位置に追加し、sitemap にも載せた。ポリシーは一般論ではなく実装の事実
  （集めない項目・localStorage の中身・チェックリストの条件は処理するが保存もログもしない・
  ログの許可リスト・IPはチャットの連続利用制限のみ・Cookieと解析なし・外部送信先はAIモデルと
  地理院タイルの2つ）を書いた。ライセンスはコード MIT（`LICENSE`）、データは出典側の規約に従う
  （`LICENSE-DATA.md`）。

- 2026-09-24: **2・4 を実装し、A-1 は完了**。
  - 2: Googleフォーム「スミハジメ 誤りのご報告・お問い合わせ」を公開（メールアドレス収集なし・
    ログイン不要・回答はGmailへ通知）。フッター・規約・ポリシーに加え、**手続き詳細の根拠カードの直後**に
    「この手続きの誤りを報告する」を置き、手続き名・自治体コード・ページURLを事前入力して開く
    （利用者の入力条件は載せない）。
  - 4: `/api/health` が自己判定（`status` / `issues`: D1不達・公開データ0件・巡回未実行/停止）を返す。
    見張り役は Google Apps Script「スミハジメ 外形監視」（maintainer のアカウント。`ops/monitoring/health-monitor.gs`
    と同一内容）で、15分ごとに正典・ミラーの health・トップ・チェックリスト作成を確かめ、異常が30分続いたとき
    と復旧したときだけGmailへ通知する。故意に壊した宛先で3項目すべてが異常として出ることを確認済み。
    運用手順は `docs/ops/monitoring.md`。

#### 初回巡回で分かったこと（2026-09-23 時点、190/332件を巡回。2026-09-24 に全332件が一巡し、再確認中は72件）

| 結果                        | 件数   | 意味                                                                               |
| --------------------------- | ------ | ---------------------------------------------------------------------------------- |
| 更新日が同じ                | 100    | 承認時から変わっていない                                                           |
| **更新日が変わった**        | **34** | 7〜8月の承認以降に自治体が更新した。再監査待ち                                     |
| 基準を確立（Last-Modified） | 24     | 更新日表記が無く、今回が初回の基準取り                                             |
| csv/xlsx のハッシュ一致     | 14     | 変わっていない                                                                     |
| 検証不能                    | 15     | 更新日もヘッダも無い5件 + 許可リスト漏れ10件（港区・荒川区。修正済みで次周に解消） |

**再監査が律速になることが数字で出た。** 全332件を一巡すると要確認は60件前後まで増える見込み。
1件あたり「公式ページを読む→台帳の根拠を照合→必要なら正規化データを直す→承認→再publish」で、
これは人手承認（A-3でOSS化して開く対象）そのもの。**まず自分で数件回して手順書にし、
1件あたりの所要時間を実測する**のが次の一手。

### A-2 都内拡大 — 市部を人口順に

未対応39自治体 = 市部26 + 町村部13。

- **市部は人口順に進める。** 八王子（約58万）・町田（約43万）・府中・調布・西東京・小平・三鷹・日野・立川・
  東村山。上位10市で多摩地域の人口の大半を占める。
- **町村部13は別途判断。** 合計しても都民の1%未満（檜原村 約2,000人、青ヶ島村 約170人）。
  「東京都全域対応」という看板の価値と、13件分の監査・承認コストを天秤にかける。
  データが極端に薄い自治体もあり、無理に作ると「対応済みに見せる」（原則9）と衝突しうる。
- **他府県は都内62が終わってから。** ブランドが「東京の新生活ToDo」であり、区をまたぐ転居が多い
  東京だからこそ「同じ手続きで期限が区で違う」が刺さる。他府県は市場が別で、名称も設計し直しになる。
  まず都内で「手順が23区の外でも通用するか」を確かめる（市部は区部とデータの出方が違う）。

追加の手順は確立済み（監査→原文スナップショット→正規化→ルール→人手承認→公開ゲート→本番→評価）。
23区の実績では、1区あたり数時間の機械作業＋人手承認1回。

### A-3 OSS化 — 承認に参加できる形へ開く

律速は人手承認で、1人では39市町村を捌けない。提出フォーム1-9で「OSSとして公開し、
自治体やシビックテックが承認に参加できる形へ開く」と書いた。これを果たす。

前提: A-1の5（ライセンス）と、外部の人が読める手順書（いまの `add-municipality` スキルは
Claude Code向けの書き方）。承認ゲートがコードで強制されているので、参加者が増えても基準は緩まない。

### A-4 Jev（typesafe.ai）— 任意・小さく

型付きの判断（Choice/Score/Noul）を返す分類モデル。嵌まるのは**チャットの意図判定**と
**RAGの保留判定**の2箇所だけ。**該当判定（原則1）と公開データには使わない。**
試すなら意図判定1箇所に限定し、179問の評価でキーワード方式との差を実測してから判断する。
一般公開の律速は人手承認であってモデルではないので、優先度は低い。

## Phase B: 収益化（Aで使われている実績が出てから）

**中立性との緊張がある。** ADR-009で「特定の事業者名を出さない」と決めており、
広告やアフィリエイトはそれと真正面から衝突する（水道・電気・ガスのタスクに事業者の広告が
出る状態は避けたい）。

筋が良いのは、**相手が利用者にスミハジメを勧める形**のB2B。

| 相手                     | 形                                        | 中立性                                   |
| ------------------------ | ----------------------------------------- | ---------------------------------------- |
| 引越し事業者・不動産会社 | 顧客向けに埋め込み／リンク提供            | 保てる（スミハジメ側は事業者を推さない） |
| 企業の人事・総務         | 転勤者向けに社内提供                      | 保てる                                   |
| 自治体                   | 住民サービスとしての提供（Phase Cの前段） | 保てる                                   |
| 個人への有料プラン       | —                                         | 行政手続き情報に個人が払う見込みは薄い   |

前提: 個人のままでは法人の調達に乗りにくい。**開業届または法人化**、B2B向けの利用規約・免責・
可用性の目安（SLAと呼ぶかは別）。非公式サービスであることをどう説明するかも決める。

### 広告の扱い（2026-09-22 ユーザー意向: 広告をメインに）

**入れてよいが、主軸にはならない。** 期待値を現実に合わせておく。

- 収益の現実: 日本語サイトのAdSenseは目安で1,000PVあたり100〜500円。転入手続きのサイトは
  3〜4月に集中し、1人あたり数ページを1回見て終わる。月3万円でも6万〜30万PV/月が要る。
  ホスティングとチャットの実費を賄う程度と見るのが妥当。
- 信頼との衝突: 文脈連動広告は引越し・電力・ガス・回線の広告を出す。ADR-009の中立性と
  正面から当たる。
- **配置ルール**（守れないなら入れない）:
  1. 「区以外の手続き」のページとタスクには出さない（水道・電気・ガス・郵便・免許）
  2. チェックリスト本体・手続き詳細の本文には出さない。出すならトップ・透明性ページ・フッター周辺
  3. 「広告」と明示する
  4. 公式根拠カードや最終確認日の近くに置かない（根拠と広告を視覚的に混ぜない）
- 前提: AdSenseの審査には利用規約・プライバシーポリシーのページが必須（A-1の3）。

位置づけは**補助収入**。本命はB2B（上表）のまま。

## Phase C: 自治体への移管

橋渡しになるのは **A-3のOSS化で、ある区の職員がレビューに参加している状態**。
既に承認に関わっていれば、引き取りは自然な延長になる。

技術的には移管しやすい設計になっている。全データが出典と最終確認日つきで追跡でき、
ライセンスと帰属を台帳で管理している（原則10）。障壁は技術ではなく、非公式→公式の
組織的・法的な移行。

## 最初の一手

**A-1から。** 拡大して利用者が増えるほど、データが古くなり誤り報告の窓口も無い状態は痛くなる。
とくにA-1の1（差分検知の定期実行）は、このサービスの中核の約束に直結する。

A-1が済んだら、A-2の上位市（八王子・町田・府中）を自分で追加して「手順が区部の外でも通用するか」を
確かめ、そのうえでA-3で開く。
