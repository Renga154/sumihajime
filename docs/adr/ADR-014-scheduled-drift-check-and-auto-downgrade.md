# ADR-014: 公式ソースの差分を定期巡回で検知し、根拠が揺らいだ手続きを自動で「要確認」へ落とす

- Status: **Accepted — 2026-09-22**（同日に main から正典・ミラーへ本番反映。初回巡回10件で changed 3・unverifiable 3・ok 4 を確認）
- Date: 2026-09-22
- 関連: CLAUDE.md 原則2(公式根拠と最終確認日)・原則3(根拠がなければ要確認)・原則8(RAG障害時も
  チェックリストは使える)、ADR-007(公開単位=人手承認済みのみ)、ADR-008(正典は個人アカウント=Workers Free)、
  `docs/ROADMAP.md` A-1-1

## Context

提出フォーム1-9に「運用ループを実装済み」と書いたが、実態は `scripts/ingest`（再取得・生バイトの
SHA-256比較・台帳の pending 降格）という**手動実行の部品**があるだけで、定期実行も、本番で見えている
手続きへの反映も繋がっていなかった。放置すると「最終確認日つきの公式根拠」という中核の約束が黙って古くなる。

設計の前に、承認済み332件から標本20件を実際に再取得して測った（2026-09-22）。

| 比較方法                                     | 不一致    | 内訳                                                                                |
| -------------------------------------------- | --------- | ----------------------------------------------------------------------------------- |
| 生バイトの SHA-256（台帳 `content_hash`）    | **14/20** | CSRFトークン・広告・ナビの揺れ。実質すべて誤検知                                    |
| 本文テキスト（`extractTextLines`）のハッシュ | 9/20      | 本当の更新4 + 「更新日」変更のみ2 + チャット導線/サイドバーの揺れ2 + 不明1          |
| ページ自身の「更新日」表記                   | 4/20      | **4件すべてが実際の本文更新**（医療証の色、AI電話の告知、持ち物の追記、更新日のみ） |

つまり生ハッシュは信号にならず、本文ハッシュもノイズが1〜2割残る。一方、自治体サイトが自分で掲げる
「更新日：令和8年9月15日」の変化は、標本内で誤検知ゼロだった。「自治体が更新したと宣言した」ことを
そのまま信号にするのが最も正直で、CPUも要らない。

制約: 正典はWorkers **Free**（1回の実行でCPU 10ms・外部サブリクエスト50・Cronは5本まで）。
リポジトリにはリモートが無く、GitHub Actions等の外部ジョブは使えない。通知先の外部サービスも無い。

## Decision

### 1. 信号は「到達性」と「ページの更新日」。生ハッシュは使わない

| 種別                            | 信号                                                                                                       | 判定                                                     |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 全ソース                        | HTTP 200 以外／最終URLのホストが変わった／パスがトップへ潰れた                                             | `unreachable`（2回連続で確定）                           |
| HTML（更新日表記あり: 248/306） | 「更新日・最終更新日」ラベルの直後の日付を抽出し、**承認時スナップショットから同じ抽出器で得た値**と比べる | 違えば `changed`                                         |
| HTML（更新日表記なし: 57）      | 初回巡回で控えた `Last-Modified` ヘッダと比べる。無ければ到達性のみ                                        | 違えば `changed`。ヘッダも無ければ `unverifiable` を記録 |
| csv / xlsx（26件・最大348KB）   | 生バイトの SHA-256 と台帳 `content_hash`（静的ファイルは生ハッシュが安定する）                             | 違えば `changed`                                         |

基準値は台帳の `source_last_modified_at`（人手記入）ではなく、**承認時スナップショットから同じ抽出器で
機械的に得た値**を使う。人手記入値は248件中17件が本文表記と食い違っており（千代田・江戸川に集中）、
比較の基準にすると初回から誤検知する。publish 時にスナップショットを読んで `sources.snapshot_page_updated_on`
へ入れる。抽出器は publish（Node）と Worker で同じ純関数を共有する（`packages/drift`）。

### 2. 降格は自動、復帰は人手のみ

- `changed` / `unreachable` になったソースを根拠に持つ手続きは、読み出し時に `dataStatus` を
  **`stale`（再確認中）** として返す。公開データ（`procedure_versions`）は書き換えない。
  チェックリストからは消さず、公式リンクも残す（原則8）。根拠カードには検知日を出す。
- 復帰の条件は「人が再確認して台帳の `last_verified_at` を進め、再publishした」こと。検知記録は
  検知時点の `last_verified_at` を控えており、ソース側がそれより新しくなった時点で効力を失う。
  **機械が `verified` へ戻すことはない**（最終確認日は人の確認日のまま）。
- 生ハッシュ・本文ハッシュによる深い差分は、これまでどおり人が `scripts/ingest` で見る（再監査の入口）。

### 3. 実行は Worker の Cron、Free の枠内で小さく回す

- `apps/api` に `scheduled` ハンドラを足し、**毎時**（`0 * * * *`）巡回する。1回に処理するのは
  `last_checked_at` が最も古い承認済みソース **10件**（外部サブリクエストはリダイレクト込みで50未満、
  CPUは本文抽出をしないので数ms以内）。332件は約1.4日で一巡する。
- 状態は D1 の `source_drift`（ソースごとに1行: 状態・検知日・検知時の `last_verified_at`・
  連続失敗回数・`Last-Modified` 基準値・詳細JSON）。publish の DELETE→INSERT 対象には**含めない**
  （巡回の記憶は公開データと独立に残る）。
- 通知は外部サービスに頼らず、`/api/health` に巡回の要約（要確認ソース数・最終巡回時刻）を含める。
  A-1-4（死活監視）で入れる外形監視がこの値を見張れば、通知は追加コストなしで成立する。
  対応状況ページにも「機械巡回の状況」として同じ要約を公開する（原則9: 検知できないものは検知できないと示す）。

## Consequences

- 良い点: 中核の約束（根拠が揺らいだら黙って古くならない）が本当に動く。判定は決定的で、
  自治体の宣言（更新日）に基づくため説明しやすい。Free の枠内・外部依存ゼロ・秘密情報ゼロ。
- 悪い点/限界:
  - 更新日表記もヘッダも無い25件程度は到達性しか見られない。これは隠さず `unverifiable` として数に出す。
  - 「更新日が変わった」は「手続きの内容が変わった」を意味しない（医療証の色が変わっただけでも要確認になる）。
    保守的に倒す設計であり、要確認の解除には人の再監査が要る。再監査が滞ると要確認が積み上がる。
  - 初回巡回は承認（7〜8月）からの空白期間の変化をまとめて拾うため、最初の数日は要確認が一時的に増える。
- 見送ったもの: 本文テキストのハッシュ比較（Free の CPU 10ms に収まらず、ノイズも残る）、
  GitHub Actions（リモート無し）、メール/Webhook通知（秘密情報とサービス契約が要る。A-1-4で外形監視に相乗り）。

## 検証

- 純関数（更新日抽出・判定）の正例・負例・境界（令和/西暦/区切り・ラベルと日付の間にタグがある渋谷区型・
  日付無し・非UTF-8宣言）。
- D1統合: 巡回→`changed`→チェックリストと詳細が `stale` と検知日を返す／再publishで `last_verified_at` が
  進めば解除される／`unreachable` は2回連続で初めて確定する／自治体スコープを越えて影響しない。
- 本番: デプロイ後に `scheduled` を手動起動（`wrangler dev --test-scheduled` または初回Cron）し、
  `/api/health` の要約と D1 の `source_drift` を確認する。
- 実施結果（2026-09-22、`wrangler dev --remote --test-scheduled` で正典D1に対して1バッチ起動）:
  10件中 changed 3（千代田 childcare: 更新日 2026-02-27→08-03 の本当の更新／utilities_contact と
  driver_license: **承認時スナップショットが取り違えられていた**ことによる基準値の誤り）、
  unverifiable 3（更新日表記もヘッダも無い都の水道・下水道、スナップショット未保存の都の市区町村一覧）、
  ok 4。japanpost は Last-Modified で基準を確立。チェックリスト・詳細・対応状況ページに反映を確認。
  取り違えの2件とスナップショット未保存の1件は再監査対象（人手承認が要る）。
