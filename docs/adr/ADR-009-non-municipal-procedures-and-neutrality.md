# ADR-009: 自治体以外の引越し手続きの扱いと中立性の原則

- Status: **Accepted — 2026-08-06(ユーザー決裁 2026-08-02「水道・郵便・免許・電気ガスを提出前に実装」)**
- Date: 2026-08-06
- 関連: REQUIREMENTS.md §5.3 P2「電気、ガス、水道、通信、郵便等の民間・国サービス連携」の前倒し、CLAUDE.md 原則2(公式根拠)・原則3(推測しない)・原則4(自治体を混ぜない)・原則5(非公式まとめサイトを一次根拠にしない)・原則9(未対応を対応済みに見せない)、ADR-007(公開単位=verifiedのみ)

## Context

転入者のToDoは、区(自治体)の窓口で完結しない。転入届と同じタイミングで、区以外の主体に対する手続きが必ず発生する。

- 水道(下水道を含む) — 東京都水道局
- 郵便物の転送 — 日本郵便株式会社
- 電気・ガス — 契約先の民間事業者
- 運転免許証の記載事項変更 — 警視庁

これらが抜けると、本プロダクトの「引越しに必要な手続きを網羅する」という約束が実態と合わない。一方で、これまでの設計は「1つの区のデータだけを混ぜずに提示する」ことを不変条件として作られており、区に属さない手続きを素朴に足すとその不変条件を壊しうる。

特に電気・ガスは、契約先が利用者ごとに異なるうえ、この領域には比較サイト・切替の営業目的サイトが大量にある。公共サービスとして、特定事業者へ誘導することは許されない。

## Decision

### 1. データのスコープ: 「全区共通」という新スコープは作らない

追加する4手続きは **各対応区の `municipalityCode` を持つ**。共通テンプレートから対応区の数だけ機械生成し、`municipalityCode` 以外は完全に同一の内容とする(`packages/rules/src/non-municipal.test.ts` が全区の一致を機械検証する)。

なぜ「全区共通」スコープを作らないか: 既存の不変条件「Profile の自治体と RuleSet の自治体が一致しなければ `MunicipalityScopeMismatchError` で評価を止める」「公開物は自治体単位で引ける」は、原則4を型と実行時の両方で守る仕組みである。ここに「どの区にも属さないレコード」を導入すると、その分岐が全経路(評価器・publish・D1・API・UI)に波及し、混入検知の意味が弱まる。データ量の重複(7区×4件)は、この不変条件を保つ対価として妥当と判断した。

スキーマ変更は行わない。`canonicalType` / `category` は自由文字列であり、`water_supply` / `postal_forwarding` / `utilities_contact` / `driver_license` をそのまま使える。

### 2. ソースのスコープ: `13000` = 東京都の機関、`00000` = 国/全国

出典(registry.csv)は区ではなく提供主体に紐づける。

| sourceId                          | 提供主体         | municipality_code |
| --------------------------------- | ---------------- | ----------------- |
| `src-13000-water_supply-001`      | 東京都水道局     | 13000             |
| `src-13000-sewerage-001`          | 東京都下水道局   | 13000             |
| `src-13000-driver_license-001`    | 警視庁           | 13000             |
| `src-00000-postal_forwarding-001` | 日本郵便株式会社 | 00000             |
| `src-00000-utilities_contact-001` | デジタル庁       | 00000             |

`13000` は `src-13000-municipalities-001`(東京都リンク集)の前例に倣う。`00000` は国/全国共通を表す新しい値だが、`municipalityCodeSchema`(5桁)を満たすためスキーマ変更は不要。透明性ページの出典一覧では、区名と取り違えないよう「東京都（都の機関）」「国・全国共通（区以外）」という見出しにする。

### 3. 電気・ガスの中立性

**特定の電力会社・ガス会社・民間の引越しポータル事業者を名指ししない。**

- 根拠とリンクは、国(デジタル庁)の公式ページ「引越し手続オンラインサービス」のみとする。同ページは「ライフライン(電気・ガス・水道)等の民間手続も含め」引越しに手続きが必要であることを示すが、事業者名は挙げていない。
- 契約先の確認方法は「検針票・請求書・契約先のマイページ等」という一般的な案内にとどめ、事業者比較・切替の情報は扱わない。
- `onlineUrl` を持たせない(オンライン申請先を特定しない)。`channels` も空にする(手続き方法は契約先により異なり、公式に確定していないため推測しない)。
- 必要書類は `status: 'unknown'`(未知を未知と明示する)。

この中立性は文章の心がけではなく**テストで固定する**。`packages/rules/src/non-municipal.test.ts` が、4手続きのあらゆる利用者向け文言に対して事業者名の denylist を突き合わせ、1つでも現れたら失敗する。

### 4. 期限は公式に明記がある場合のみ日数にする

4件とも `dueRule: { type: 'unknown' }` とし、`dueDescription` に公式文言を載せる。監査で確認した事実:

- **水道**: 東京都水道局は「次のお手続きについては、3〜4日前までに必ずお手続きください」と案内する。これは**引越し日より前**を指す前倒しの表現であり、`dueRule` の `offsetDays`(`days` は非負=引越し日以降)では表現できない。負のオフセットを足すスキーマ変更はせず、公式文言をそのまま提示する。
- **郵便**: 「転居届を提出されてから登録までに3〜7営業日を要します」は**処理に要する日数**であって期限ではない。期限へ変換しない。
- **電気・ガス / 運転免許**: 出典に日数の記載が一切ない。「記載がありません(要確認)」と明示する。

結果として4件は期限順の並びで「生活開始」に置かれ、転入届などの期限つき手続きより後に来る。優先度も `normal`(転入届 `urgent` / マイナンバー `high` より低い)とする。

### 5. RAGコーパスには追加しない

`scripts/rag/src/manifest.ts` の `RAG_MUNICIPALITIES` は対応7区のままとし、13000/00000 のスナップショットは索引しない(コード変更なしで自然に除外される)。

なぜか: チャットは「選択した1自治体のスコープに強制する」ことで自治体をまたぐ回答混入を防いでいる。区に属さないチャンクを同じコーパスに入れることは、そのスコープ強制に例外を作ることであり、混入検知の評価(50問)の前提も作り直しになる。この4手続きはチェックリストと公式リンクで完結するため、チャットの安全性を優先する。

### 6. 公開はしない(人手レビュー承認まで)

出典5件は `review_status=pending`、手続き4件は `dataStatus=partial` とする。ADR-007 により publish は verified の手続きだけを D1 へ載せるため、承認まで利用者には表示されない。`rules.json` の `ruleVersion` は前進させるが、公開される部分集合(区の10ルール)は内容が不変のため `publishedRuleVersion` に旧版を据え置く(ADR-007 §5)。`coverage.csv` には `non_municipal` 列を追加し、承認まで `unavailable` とする。

### 7. UIでは「区の手続き」と「区以外の手続き」を区別する

チェックリストのカードに「区以外の手続き」バッジを1つ出す(`apps/web/src/lib/provider-scope.ts` の純関数がカテゴリだけで判定する)。未知のカテゴリは安全側に倒して「区の手続き」扱いにし、根拠なく「区以外」と表示しない。区の窓口一覧(FacilitiesPage)には警視庁等の施設を混ぜない。

## Consequences

- 転入者にとってのToDoが、区の窓口で完結しない現実に追いつく。
- 区のデータと非区のデータは `municipalityCode` で最後まで分離されるため、原則4の検証(越境テスト・混入検知)はこれまでと同じ形のまま通用する。
- 手続きの文言が7区に重複する。文言を直すときは共通テンプレートから再生成し、全区一致テストが差分を検出する。
- 電気・ガスは「何をすればよいか」の粒度が粗い(契約先が特定できないため)。これは中立性と原則3のための意図的な縮退であり、事業者名や比較情報で埋めない。
- 承認後にやること: registry.csv の5件を approved へ、procedures.json の4件を verified へ、rules.json の `publishedRuleVersion` を除去、`coverage.csv` の `non_municipal` を verified へ、`non-municipal.test.ts` の pending 期待値を approved へ更新。

## Alternatives considered

1. **(A) 「全区共通」スコープ(municipalityCode を持たないレコード)を新設する**。データ重複は消えるが、自治体スコープの不変条件に例外が生まれ、評価器・publish・API・UI の全経路へ分岐が波及する。棄却。
2. **(B) 電気・ガスで主要事業者を列挙する**。利用者には親切だが、公共サービスとしての中立性を損ない、網羅性も担保できない(新電力は多数)。棄却。
3. **(C) 水道の期限を「引越し日−4日」として dueDate を算定する**。`dueRule` に負のオフセットを足すスキーマ変更が必要で、かつ「3〜4日前まで」の幅を1点の日付に丸めることになる。公式文言の提示にとどめる。棄却。
4. **(D) RAGコーパスへ追加する**。チャットで水道・郵便も答えられるようになるが、自治体スコープ強制の例外を作る。将来、非自治体スコープの扱いを設計しなおすときに再検討する。棄却(現時点)。
