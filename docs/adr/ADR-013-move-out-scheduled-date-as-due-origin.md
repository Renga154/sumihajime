# ADR-013: 前住所地の転出予定日を任意入力として受け取り、期限の起算日に加える

- Status: **Proposed — 2026-08-09**（本番反映は未実施。デプロイは main から一括で行う）
- Date: 2026-08-09
- 関連: REQUIREMENTS.md §7.3(入力ウィザード)・§9.2(ルール入力)・§10(期限表示)・§13(データ最小化)、CLAUDE.md 原則2(公式根拠)・原則3(推測しない)・原則4(自治体を混ぜない)・原則6/7(個人情報を集めない・残さない)、ADR-002(ルールDSL)、ADR-007(公開単位=verifiedのみ)

## Context

独立点検の指摘: 全条件ONのペルソナで23区322タスクを評価すると、実際に日付が出るのは55件（17%）だけで、
残りは「期限は要確認」だった。「期限順のToDo」を掲げるサービスとして中核の訴求が薄い。

原因を1件ずつ追うと、**推測を避けた結果**であると同時に、**公式ページが実際に日数を書いているのに
算定していない**ケースが3種類あった。

1. **児童手当の15日特例** — 23区中19区が「前住所地の転出予定日の翌日から15日以内」と明記している。
   例: 板橋区「出生日・転入日（前住所地の転出予定日）等の事由発生日の翌日から起算して15日以内」。
   起算日が転出予定日なので引越し日からは算定できず、**アプリがその日付を訊いていなかった**。
2. **マイナンバーカードの継続利用** — 継続利用そのものの期限（転入届出日から90日）は起算日を知り得ない。
   しかし多くの区は、同じページで**転入届側の条件**（住み始めた日から14日以内／前住所地の転出予定日から
   30日以内）を「これを満たさないとカードが失効する」と明記している。これは持っている日付から算定できる。
3. **子ども医療費助成** — 3区が「転入日から14日以内／15日以内」と日数で明記しているのに `unknown` だった。

## Decision

### 1. Profile に `moveOutScheduledDate`（前住所地の転出予定日）を任意項目として足す

- `profileSchema`（`packages/schemas/src/profile.ts`）は `strictObject` で、そのまま
  `POST /api/checklists` の本体になる。`z.iso.date().optional()` として追加する。
- **任意**にする。まだ転出届を出していない・値を覚えていない利用者を入力で止めないため。
  未入力なら**期日を算定しない**（引越し日で代用しない）。
- 収集するのは暦日1つだけで、前住所地の自治体名・住所は受け取らない。氏名・電話・完全な生年月日等は
  従来どおり入力欄自体を持たない（原則6）。保存先は端末内 localStorage のみで、サーバーへ保存しない。
- 後方互換: `optional` のため、この項目を持たない既存の保存済みプロフィールもそのまま parse できる。
  ウィザードの下書きスキーマ側は `.default('')` で古い下書きも読めるようにする。

### 2. ルールDSLの起算日に `moveOutScheduledDate` を足し、`earliestOf` を導入する

```
dueRule: { type: 'offsetDays', from: 'moveDate' | 'moveOutScheduledDate', days: n }
dueRule: { type: 'earliestOf', of: [offsetDays, offsetDays, ...] }   // 2件以上
dueRule: { type: 'unknown' }
```

- 起算日の語彙は **Profile が実際に持つ暦日だけ**に限る。「転入届出日」は足さない。その日は本サービスが
  知り得ず（大半の利用者はまだ届出していない）、語彙に持たせると推測で埋める余地を構造的に残すため。
- `earliestOf` が必要な理由: 区は複数の失効条件を並べて書く。例）板橋区「住み始めた日から14日以内
  **または** 転出予定日から30日以内の**どちらか早い期日**まで」。片方だけを期日にすると、もう片方が
  先に来る利用者に**実際より遅い期日**を見せてしまい、カード失効という実害につながる。
  算定できない候補（転出予定日が未入力など）は無視し、1つも算定できなければ期日を出さない。
- 日付計算は既存の Asia/Tokyo 非依存ユーティリティ（`packages/rules/src/dates.ts`、`Date.UTC` 系のみ）を
  そのまま使う。月末・年跨ぎ・閏日の境界はテストで固定する。

### 3. ルールは「その区の公式ページが書いていること」だけを根拠に入れる

| 手続き                     | 算定する区                                         | 根拠                                             |
| -------------------------- | -------------------------------------------------- | ------------------------------------------------ |
| 児童手当（15日特例）       | 19区（転出予定日 +15日）                           | 「前住所地の転出予定日の翌日から15日以内」の明記 |
| 子ども医療費助成           | 3区（渋谷14 / 杉並15 / 板橋14、いずれも引越し日）  | 「転入日から N日以内」と**日数で**明記           |
| マイナンバーカード継続利用 | 17区（引越し日+14 or 15 / 転出予定日+30 の早い方） | カード失効の条件として区が明記した転入届側の期限 |

算定**しない**と決めた区とその理由:

- 千代田・墨田（マイナンバー）… カード失効の条件として書いているのは90日だけ。ページ中の「14日以内」は
  住民異動届一般の届出期間で、カード失効に結び付けて書かれていない。
- 目黒（マイナンバー）… 「他区にある30日・14日の失効条件の記載がありません」と区自身が明記している。
- 港・台東・北（マイナンバー）… 継続利用の期限そのものを公式ページで確認できないと区自身が明記。
  **記載の無い区に90日を当てはめない。**
- 品川（マイナンバーの30日）… 条件は「引っ越し**予定日**から30日以内」で「転出予定日」の語を使っておらず、
  何の予定日かを公式ページから確定できない。14日側だけを採る。
- 港・墨田（子ども医療費）… 「転入日から15日以内」と日数はあるが、同じ区の児童手当ページは
  『転入日＝前住所地の転出予定日』と定義している。子ども医療費のページにその定義が無く、
  15日をどちらの日から数えるか確定できない。
- 月単位（3か月・6か月など）で書く13区（子ども医療費）… 暦月の数え方（応当日が無い月の扱い）を
  公式ページが書いていない。日付に変換すると、公式が言っていない日を作ることになる。

### 4. チェックリストから「入れれば期限を出せる」ことを伝える（2026-08-09 追記）

任意項目である以上、多くの利用者は空欄のまま進む。その人は**入れれば日付が出せると知らないまま**
「期限は要確認」を見ることになる。チェックリスト画面に案内を置く。

出す条件（すべて満たすときだけ）:

1. `moveOutScheduledDate` が未入力。
2. **その人のチェックリストに**、転出予定日を起算日とする手続きが実際にある。
3. `originType` が `overseas` でない（前住所地が国外なら日本の市区町村へ転出届を出しておらず、
   「転出予定日」という日付自体が存在しない。ウィザードの説明文でも入力不要と書いている）。
4. 手続き名を1件以上出せる（名前を出せないなら一般論になるので出さない）。

判定材料は `POST /api/checklists` の応答に足す `moveOutScheduledDateImpact` だけとする:

```
moveOutScheduledDateImpact: {
  enablesDueDateFor:  procedureId[]  // いま期日なし → 入れれば日付が出る
  advancesDueDateFor: procedureId[]  // 既に期日あり → 入れるとより早い期日に変わりうる(earliestOf)
}
```

- **なぜAPIが返すか**: どの手続きがどの日付を起算日にしているかは区ごとのルールデータにしかない。
  UI側で判断すると区コードの分岐を画面へ書くことになり、CLAUDE.md §4（自治体固有ロジックをUIへ
  埋め込まない）に反する。判定は `@tmn/rules` の純関数 `moveOutScheduledDateImpact(profile, ruleSet)`
  が行い、画面は受け取った procedureId を同じ応答の `tasks[].title` と突き合わせて名前を出すだけにする。
- **なぜ仮の日付で再評価しないか**: `earliestOf` は入れた値次第で結果が変わるため、入力前に
  「何が起きるか」を決め打ちできない。`dueRule` の構造だけから、どんな値でも成り立つ2つ
  （必ず日付が出る／遅くはならない）に限って言う。
- **なぜ `advancesDueDateFor` を分けるか**: 未入力のとき `earliestOf` は引越し日側の候補だけを採るため、
  実際より**遅い**期日を表示していることがある。マイナンバーカードの失効という実害に直結するので、
  「既に日付が出ている」ことを理由に黙らない。ただし早くなるかは値次第なので「変わることがあります」と言う。
- **なぜ optional か**: 端末内の控え（checklist-cache）は同じスキーマで読み直す。必須にすると
  この項目より前に保存された控えが丸ごと読めなくなり、電波の弱い場所でチェックリスト本体を失う（原則8）。
- `not_applicable` の手続き（子どものいない世帯の児童手当など）は対象にしない。無関係な人へ出す案内は
  案内自体の価値を下げる。

23区の実測（全条件ONのペルソナ）: 案内が出るのは20区、出ないのは**千代田・台東・北**の3区
（この3区は転出予定日を起算日とするルールを1件も持たない）。新宿は児童手当が転出予定日起算ではないが、
マイナンバーが `earliestOf` なので `advancesDueDateFor` だけで案内が出る。
ステップ2・3を通らなかった単身の成人には、23区すべてで案内が出ない。

### 5. 比較ページ（/differences）の分類は変えない

`GET /api/ward-differences` の分類は**区が書いた文言から導出**し、期日は**ルールから導出**する。
両者を二重帳簿にしない。マイナンバーの分類（90日明記18区 / 90日でない期限を明記2区 / 記載なし3区）は
今回の変更後も同じであることをテストで固定した。児童手当の「転出予定日が起算日」のラベルだけ、
「入力があればその日から算定／引越し日からは算定できない」と現在の挙動に合わせて更新した。

## Consequences

### 良くなること

全条件ONのペルソナ（23区322タスク）で日付が出るタスク数:

| 状態                           | 件数 | 割合 |
| ------------------------------ | ---- | ---- |
| 変更前                         | 55   | 17%  |
| 変更後・転出予定日を入力しない | 70   | 22%  |
| 変更後・転出予定日を入力する   | 92   | 29%  |

### 引き受けるリスク・制約

- **入力が増える**。任意ではあるが、ステップ1に日付欄が1つ増える。未入力でも従来どおり動く。
- **転出予定日の正確さは利用者に依存する**。前住所地へ届け出た日と違う値を入れれば期日もずれる。
  欄の説明文で「転出届で届け出た日・転出証明書に記載の日」であることを明示する。
- **マイナンバーの期日の意味が「継続利用の手続き期限」ではなく「カードを失効させないために転入届を
  済ませる期限」である**。手続き詳細ページには区の公式文言がそのまま出るため、条件の全体は読める。
- 月単位の期限（子ども医療費13区）は依然として日付にしていない。ここを日付にするなら、
  暦月の数え方をどう扱うかを別途決める必要がある（本ADRの範囲外）。

## Alternatives considered

- **転出予定日を必須にする**: 算定できる件数は最大化するが、まだ転出届を出していない利用者を
  入口で止める。却下。
- **未入力時は引越し日で代用する**: 区が言っていない期限を作ることになる（原則3違反）。却下。
- **マイナンバーで転出予定日+30日だけを採る**: 引越し日+14日のほうが先に来る利用者に遅い期日を
  見せてしまう。`earliestOf` を導入して両方を見る形にした。
- **`from` に「転入届出日」を足し、利用者に入力させる**: まだ届出していない利用者が大半で、
  入力できない項目を増やすだけになる。却下。
