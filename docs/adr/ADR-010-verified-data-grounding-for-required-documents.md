# ADR-010: 必要書類の回答を検証済み構造化データで根拠づける／確度表示を廃止する

- Status: **Accepted — 2026-08-08(ユーザー決裁「案A+案C採用、確度表示は削除」)**
- Date: 2026-08-08
- 関連: REQUIREMENTS.md §11(RAG)・§11.4 回答フォーマット・§11.5 保留・§11.6 出力検証、CLAUDE.md 原則1(該当判定をLLMへ任せない)・原則2(公式根拠と最終確認日)・原則3(推測しない)・原則4(自治体を混ぜない)・原則8(RAG障害時の縮退)、ADR-004(検索スコープのサーバー側強制)、ADR-007(公開単位=verifiedのみ)

## Context

### 観測された不具合

23区で「転入届に必要な持ち物は？」型の質問を実測したところ、**3区で誤答**していた。

| 区            | 症状                                                                           |
| ------------- | ------------------------------------------------------------------------------ |
| 江戸川(13123) | 「お持ちの方」限定のマイナンバーカードを**唯一の必須物**として断定。確度「高」 |
| 千代田(13101) | 必須の**転出証明書**を落とす                                                   |
| 葛飾(13122)   | 必須の**本人確認書類**を落とす。確度「高」                                     |

### 根本原因: 検索の失敗ではなく「生成段階の統合の失敗」

- 江戸川の該当チャンク4件は**すべてプロンプト窓に入っていた**。`本人確認できるもの`・『転出証明書』を含むチャンクも届いている。モデルがそれを落としていた。
- 自治体ページは持ち物を**複数の並列ブロック**で書く。江戸川は「ワンストップ／特例転出／紙の転出証明書」の場合分け、葛飾は「届出人・本人確認書類について」という節が転入・転出・転居の**上位に共通**で置かれる。モデルは**1ブロックだけを根拠に答え、統合しない**。結果、他ブロックにある無条件必須項目が消え、選んだブロックの「お持ちの方」限定項目が唯一の必須物になる。
- 制御実験: 本人確認を含むチャンク**だけ**を与えるとモデルは正しく答える。**競合する持ち物ブロックが同時に存在するときだけ失敗する**。
- プロンプト規則の非対称: `packages/rag/src/prompt.ts` の規則5b/5cは**期限・日数**に行為帰属を強制していたが、**持ち物・必要書類に相当する規則が存在しなかった**。

### すでに検証済みのデータが手元にあった

`data/normalized/<区>/procedures.json` の `requiredDocuments[]` は、

- **人手レビュー済み**（`dataStatus: verified`）
- `required` / `conditional` / `unknown` の**区別を持つ**
- `sourceIds` と `lastVerifiedAt` を持つ
- 既にD1(`procedure_versions`)に載っており、**チェックリストAPIは同じ値を返している**

にもかかわらず、チャットだけがこれを使わず**生のHTMLからLLMに再導出させていた**。同じ問いに対して、チェックリストは検証済みの構造を返し、チャットはモデルの読み取りを返すという二重基準になっていた。これはCLAUDE.md原則1「チェックリストの該当判定をLLMへ任せない」の趣旨に反する。

### 確度表示

`confidence` は `confidenceFromScore`(`packages/rag/src/answer.ts`)で**検索スコア(cosine類似度)だけ**から算出されていた。検索は成功していたので、上表の誤答にも「確度: 高」が付いていた。**回答の正しさを一切表していない指標**を確度として表示していたことになる。

## Decision

### 1. 必要書類の質問は、検証済み構造化データを根拠に答える（案A）

`POST /api/chat` に、ベクトル検索・生成より**前段**の決定論的経路を置く。

適用条件（すべて満たすときのみ。ひとつでも欠ければ従来のRAG経路へ委ねる）:

1. 質問が書類・持ち物を主題にしている（`hasDocumentIntent`。決定論的キーワード判定）
2. 質問が主題とする手続きが**ちょうど1つ**に決まる（既存の `questionCategories` を再利用）
3. その手続きの検証済みレコードが存在し、`dataStatus=verified` かつ `requiredDocuments` が空でない
4. 質問が**選択自治体以外の自治体名を含まない**（越境は規則3を持つRAG経路へ）
5. `sourceIds` が承認済み台帳へ解決でき、最終確認日を示せる

回答本文は `renderVerifiedDocumentAnswer`（純関数）が組み立てる。不変条件:

- `required` と `conditional` を**必ず別の見出しの下**に置く。「あてはまる方のみ」の書類を必須として断定しない。`required` を落とさない。
- `unknown` は「公式ページでの確認が必要なもの」として第三の区分にする（未知を必須にも条件付きにも寄せない＝原則3）。
- ラベルは**公式文言のまま**。言い換え・要約・補完をしない。
- `required` が0件なら「必ず必要なもの」見出しを出さない（空の必須を装わない）。

**LLMは事実の抽出にも整形にも関与しない。** ユーザー決裁は「LLMの役割は検証済み構造の自然文への整形に限定する」であったが、実装では整形も決定論的な純関数に置いた。理由は、本件の失敗モードが「モデルが項目を落とす」ことそのものであり、整形をモデルに任せると**同じ経路が残る**ため。純関数にすることで項目欠落は構造的に起こり得なくなり、単体テストで固定でき、生成呼び出しが消えてレイテンシとコストも下がる。決裁の意図（検証済み構造で根拠づける）はより強く満たされる。

### 2. RAG経路の一般改善（案C）

検証済みデータが無い問い合わせは従来どおりRAGで扱う。その経路にも、測定済みの軽い改善を入れる。

- **生成窓を文書順に並べる**（`orderByDocumentPosition`）。**どのチャンクを見せるか**は既存の検索＋手続き意図リランクが決め、**どの順で見せるか**だけを原文順（同一 `sourceId` 内の `seq` 昇順）へ戻す。文書間の順序は初出順＝検索スコア順を保つ。スコア順のまま提示すると節が原文と逆順・飛び飛びで並び、共通節と場合分けの関係が読み取れない。
- **規則5d の追加**。期限にだけ存在した行為帰属の規則を、持ち物・必要書類にも与える。「どの手続きの、どの場合の持ち物か」を確認させ、**抜粋の複数箇所を統合**することと、条件付き書類を条件を外して断定しないこと・無条件の書類を条件付きで置き換えて省略しないことを明示する。

再索引は不要（チャンク分割は変更しない）。実測では書類系の失敗3件→1件（千代田・江戸川が解消、退行ゼロ）。残る1件（葛飾）は案Aが引き取る。

### 3. 確度表示を廃止する

UIから「確度: 高/中/低」を削除する。非保留の回答にはバッジを出さず、保留のときだけ「要確認」を出す。`confidence` フィールドはAPIに残すが**内部値**とし、評価・計測にのみ用いる（スキーマ変更＝破壊的変更を避けるため）。構造化データ経路は `high` 固定（人手承認済みデータの提示であるため）。

利用者に示すのは「保留かどうか」と「公式根拠（出典・提供元・URL・最終確認日）」だけにする。

**REQUIREMENTS.md からの意図的な逸脱**: §11.4 の回答フォーマット項目「4. 確度または『要確認』表示」のうち、**確度の表示を行わない**。要件は「確度**または**要確認」であるため「要確認」だけを表示する実装は文面上も満たすが、確度を出さないという判断は明示的なものなのでここに記録する。要件文の改訂は行わない（CLAUDE.md §1「勝手に仕様を変えず、変更案と影響を提示する」）。要件を更新する場合は「回答の正しさを表さない指標を確度として表示しない」旨に改めることを提案する。

## RAGの契約の変更

これまでの契約は「**抜粋の範囲でのみ回答する**」だった。この契約は RAG 経路では変わらない。変わるのは、その手前に**別種の回答経路**が増えたことである。

| 経路           | 根拠                                   | 引用の意味                                                                 | 誰が事実を選ぶか |
| -------------- | -------------------------------------- | -------------------------------------------------------------------------- | ---------------- |
| 検証済みデータ | `procedure_versions.requiredDocuments` | 「この手続きレコードの出典」。人手レビューがこのレコード全体を承認した根拠 | 人（レビュー時） |
| RAG（従来）    | 検索でヒットした抜粋                   | 「この文を読んで答えた」。生成が実際に参照した抜粋                         | モデル（生成時） |

引用の意味づけが経路によって異なる点は自覚的な設計である。検証済みデータ経路の `sourceIds` は**フィールド単位ではなくレコード単位**の出自であり、`requiredDocuments` だけを指す出典ではない（例: 窓口一覧のソースが併記される区がある）。これは正規化データが元々レコード単位で出典を持つためで、フィールド単位の出典を持たせる変更は将来の課題とする。いずれの経路でも、利用者に見える約束「公式ページで確認できる根拠と最終確認日を必ず添える」は同一である。

保留の優先順位も変わらない。**誤断定より保留を優先する**。構造化データが無い・手続きが一意に決まらない・越境の疑いがある場合は、断定せずRAG経路（＝根拠が無ければ保留）へ委ねる。

## 評価指標への影響

- データセットを v2.0.0(151問) → **v2.1.0(175問)** に拡張した。正答系142・保留系17・越境系16。
- **必要書類のケースを23区すべてに追加**した。v1.2.0にあった書類系4問（うち転入届2問）が23区化のv2.0.0で全て失われ、151問中に持ち物・必要書類を問うケースが**1問も無かった**。UIのプレースホルダそのものの質問が未計測だったという回帰の是正である。`assertDatasetShape` で「全対応区に書類ケースがあること」を機械的に強制し、同じ欠落が二度起きないようにした。
- 期待値は各区の `requiredDocuments[]` に一致させる。`required` の公式文言を**すべて** `answerMustInclude` に列挙し（1つでも欠ければ fail）、`conditional` については「■ 場合により必要なもの（あてはまる方のみ）」見出しを期待値に含めることで、条件付き書類が必須として断定されていないことを検査する。
- `answerMustInclude` には回答に現れる期限トークン（例: `14日`）も併せて列挙する。これは既存の `needsHumanReviewRule`（answerMustIncludeで説明されない日数表現をレビュー対象にする）の誤発火を防ぐためで、公式文言由来の表現に限る。
- 構造化データ経路は生成呼び出しを行わないため、書類系ケースのレイテンシは大きく下がる。p95閾値(8秒)の判定は従来どおり全ケースで行う。

## Consequences

### 良い点

- 必要書類について、モデルが項目を落とす経路が**構造的に存在しなくなる**。required/conditional の区別が必ず保たれる。
- チェックリストとチャットが同じ検証済みデータを根拠にするようになり、二重基準が解消する。
- OpenAI/Vectorize が落ちていても必要書類の質問には答えられる（原則8の縮退が一段強くなる）。
- 誤解を招く確度表示が消え、利用者が見る品質シグナルが「保留か否か」と「公式根拠」に一本化される。

### 悪い点・残るリスク

- 回答が**定型的**になる（見出し＋箇条書き）。会話としての自然さは下がる。誤断定を避けることを優先した。
- 質問の細部（例: 「国外から転入する場合だけ知りたい」）に絞り込まず、その手続きの書類を**すべて**提示する。過不足のうち「不足」を避ける側に倒している。
- 対象は `questionCategories` が判定できる手続きに限られる。辞書に無い手続きの書類質問は従来どおりRAG経路（＝根拠が無ければ保留）。
- 引用がレコード単位の出自であるため、書類そのものを直接示さないソースが引用に並ぶ区がある。
- 越境ガードは自治体名の文字列一致による。台帳に無い呼称（例: 「世田谷」と区を付けない表記）は検出できない。この場合もRAG経路の規則3が二重の防御として働く。

## Alternatives considered

- **チャンク分割の変更**（持ち物ブロックを1チャンクへ寄せる等）: 実測で効果が無いか、他カテゴリへの副作用が大きく却下。再索引コストも伴う。
- **プロンプト強化のみ**（規則5dだけ）: 失敗3件→1件までは改善するが葛飾が残る。生成に事実の抽出を任せ続ける以上、同種の失敗は別の区・別の手続きで再発しうる。
- **LLMに検証済み構造を渡して整形させる**: 決裁の文面には最も近いが、項目を落とす経路が残る。純関数の整形に置き換えた（上述）。
- **`confidence` をスキーマから削除**: 破壊的変更になり、評価ハーネス・E2Eの契約にも波及する。表示をやめ内部値として残す方が影響が小さい。
