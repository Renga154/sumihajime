# ADR-012: チェックリストの端末内控えと、補助機能の障害を本体から切り離す

- Status: **Accepted — 2026-08-09**
- Date: 2026-08-09
- 関連: CLAUDE.md 原則3(推測しない・根拠がなければ未確認と表示)・原則6/7(個人情報を集めない・ログへ残さない)・原則8(RAG障害時もチェックリストと公式リンクを使えるようにする)・原則9(未対応を対応済みに見せない)、REQUIREMENTS.md §13(データ最小化)・§11(RAG)、ADR-010(検証済みデータ経路)、ADR-011(Workerのフォールバック)

## Context

独立点検の P1 として次の4点が挙がった。実装を読むと、いずれも「本体の可用性が補助機能より手薄」という同じ形をしていた。

| 事象                                 | 実装上の原因                                                                                                   |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| API不達でチェックリストが全消失      | 生成結果はメモリ上にしかなく、`POST /api/checklists` が通らなければ画面には何も残らない                        |
| チャットの描画時例外が本体を巻き込む | `ChatPanel` を囲む境界が無く、例外はルータの `errorElement` まで抜けてチェックリストごとエラー画面へ差し替わる |
| チャット欄が実態と無関係に出る       | `/api/chat/availability` が `RAG_ENABLED` しか見ておらず、鍵が失効していても「使えます」と答える               |
| 失敗しても押せるものが無い           | エラー文面は「もう一度お試しください」と言うのに再試行ボタンが無く、復帰手段はページ全体の再読み込みだけ       |

原則8 は RAG 障害時にチェックリストと公式リンクが使えることを求めているが、**守られるべき本体そのもの**の可用性は誰も守っていなかった。最悪の場面は区役所の弱い電波で、必要な手続きも、そこへ辿る公式リンクも、窓口の前で同時に失われる。

本番実測(2026-08-09、`https://app.sumihajime.workers.dev`):

```
GET /api/chat/availability → HTTP 200 {"enabled":true}
```

依存(`OPENAI_API_KEY` / `VECTORIZE`)を一切見ていないことが応答形状から確認できる。

## Decision

### 1. 生成済みチェックリストを端末内(localStorage)へ控える

`apps/web/src/lib/checklist-cache.ts`。キーは `tmn:checklist-cache:<code>`。

**保存する**: タスク一覧(件名・期限・必要書類・窓口・公式URL・最終確認日)、自治体名と自治体コード、取得時刻、適用ルールのバージョン。窓口の前で要るのはこれで、公式URLと最終確認日を伴わないタスクは表示できない(原則2)。

**保存しない**、およびその理由:

- **プロフィール本体**。控えが「今の条件の結果か」を確かめるのに必要なのは同一性だけなので、照合用の指紋(`profileDigest`)しか持たない。妊娠・障害・介護といった条件を、端末内でも2か所へ複製しない(§13)。プロフィールの正は `tmn:profile:<code>` の1か所のままにする。指紋からは条件を復元できない。
- **チャットの質問文と回答**。画面で「質問文と回答は保存もログ記録もしていません」と約束している。可用性を理由にその約束を破らない。チャットは補助機能なので、落ちたら落ちたでよい。
- **サーバー側には何も置かない**。控えは端末内だけで、送信も計測もしない。

保存先は常に最後に見た1自治体ぶんだけにする(原則4の混入防止と、端末に残す量を増やさないため)。容量超過などで書けなくても失敗させない — 控えは付加機能で、いま成功している取得を壊してよい理由にならない。

### 2. 控えは代替であって既定ではない。出すときは必ず「いつ時点か」を言う

毎回まずAPIを叩き、成功したら必ず控えを上書きする。控えを読むのは**今は届かない失敗**のときだけで、その判定はステータスで行う。

| 失敗の種類                   | 扱い                         |
| ---------------------------- | ---------------------------- |
| 通信断・時間切れ(status 0)   | 控えへ退避                   |
| 混雑(429)・サーバー不調(5xx) | 控えへ退避                   |
| 404 / 409 / 422              | 控えを**捨てて**エラーを表示 |

404/409/422 はサーバーの確定した答え(「その自治体は対象外」「入力が不正」)であり、ここで控えを出すと、取り下げ済みの案内を見せ続けることになる(原則9)。

控えを出すときは、取得時刻(日本時間)と経過日数、「これは最新の取得ではありません」、公式ページで確かめられることを必ず添える(原則3)。この告知は**印刷しても消さない**。画面では断っておきながら紙からその断りだけ落ちるのが、いちばん誤解が起きやすい形になるため。

### 3. 古い判定を出し続けないための門

1. 成功したら必ず上書きする。ルールのバージョンが変わっていれば、次に繋がった瞬間に新しい判定へ置き換わる。
2. 条件を変えたら(指紋が不一致)控えを使わず、その場で消す。修正前の判定が復活しない。
3. 保存形式が変わったら(`formatVersion` 不一致)読まずに捨てる。
4. 自治体をまたいで持たない。

オフラインではルールが変わったかどうかを知る術がない。だから**有効期限は設けず**、代わりに最新だとは決して言わない。期限で消す設計は、いちばん必要な場面(何日も繋がらない状態)で唯一の控えを黙って消してしまい、原則8に反する。古さは日付と経過日数として利用者へ渡し、判断材料にしてもらう。

### 4. Service Worker は入れない

入れれば真のオフライン(アプリシェルごと)に対応でき、見た目には強くなる。それでも入れない:

- 失われて困るのは**チェックリストの中身**で、これは localStorage で足りる。Service Worker が余分に守るのはHTML・JS・CSSであり、そこはブラウザのHTTPキャッシュが既にある程度受け持つ。
- 代償が具体的すぎる。SWは古いJSを掴み続け、更新が反映されない。本サービスは公的手続きの期限と必要書類を扱うので、「直したはずの内容が端末によって出ない」は最も避けたい壊れ方で、ADR-011 が404のキャッシュを嫌ったのと同じ理由が当てはまる。回避するには skipWaiting・clientsClaim・更新通知・バージョン整合の運用が要り、その運用を回す体制が今は無い。
- 入れずに済ませた場合の欠損は「回線が切れた状態での初回訪問」だけで、これは控えが存在しない場面なので、どのみち出せるものが無い。

得るものが小さく、失敗したときの壊れ方が重い。よって見送る。必要になるとすれば、アプリシェルのオフライン起動が要件になったときで、その際は更新戦略込みで別途決める。

### 5. チャットは境界で囲み、実際の依存を見て、失敗したらその場でやり直せるようにする

- `ErrorBoundary`(`apps/web/src/components/ErrorBoundary.tsx`)で `ChatPanel` を囲む。代替表示は原因を推測せず、(a)いま何が使えないか、(b)何がそのまま使えるか(チェックリストと公式リンク)、(c)いま押せる操作、の3点だけを書く。例外メッセージ本文はコンソールにも出さない — 描画中の値がそのまま載ることがあるため(原則7)。種類と部品名だけ残す。
- `/api/chat/availability` は `RAG_ENABLED` に加えて `OPENAI_API_KEY`(空白のみは未設定と同じ)と `VECTORIZE` を見る。応答は `{enabled, mode}` の3値。

  | 状態                   | mode             | UI                                       |
  | ---------------------- | ---------------- | ---------------------------------------- |
  | フラグ・鍵・索引が揃う | `full`           | 通常のチャット欄                         |
  | 鍵または索引が無い     | `documents_only` | 「必要な持ち物・書類のみ」と送信前に告知 |
  | フラグ無効             | `disabled`       | パネルを描画しない                       |

  縮退時に `enabled=false` にしないのは、鍵も索引も無い状態で唯一動くのが検証済み構造化データ経路(ADR-010)だからである。この経路はRAG基盤の障害時に答えられるよう意図的にLLM呼び出しより前に置かれており(原則8)、ここで一律に隠すと障害時にこそ効く経路まで一緒に落ちる。

  判定は**バインディングと設定の有無だけ**で行い、外部APIを呼ばない。鍵の有効性を確かめるには OpenAI への実リクエストが要り、表示可否のためだけに画面表示のたび課金と外部依存を増やすのは割に合わない。ここで検出できるのは「設定が無い」までで、「鍵が拒否される」は送信時の503と再試行導線で受け止める。`mode` はクライアント側で省略可能に扱う(欠けていれば `full` とみなす)ため、サーバーとUIのデプロイ順を揃える必要はない。

- 併せて `handleChat` の索引チェックを埋め込み生成より**前**へ移した。以前は `embedText`(OpenAIへの課金リクエスト)を済ませてから `VECTORIZE` の有無を確かめており、索引が外れている間は返せないと分かっている応答のために毎回課金していた。
- `useAsync` に `reload()` を足し、`ErrorMessage` に再試行ボタンを持たせて全ページへ配線した。チャットは「失敗したその質問」を送り直せる(入力欄を編集していても、押した時点の文面を控えてある)。
- チェックリストの取得は `Promise.allSettled` にした。自治体名を引く `GET /api/municipalities` は見出しの飾りで、これが落ちただけで生成に成功したチェックリストを消す理由にならない。

## Consequences

- 端末内に手続き一覧が残るため、条件から導かれる情報(子育て・介護など)が localStorage に置かれる。プロフィールが既に同じ端末・同じ格納庫にあるので新たな露出面は増えないが、控えは1自治体ぶんに限り、条件変更・形式変更で消える。
- オフラインで表示した内容が古い可能性は残る。これは表示側の告知(取得時刻・経過日数・公式ページ導線)で受け止める設計で、消せるものではない。
- 真のオフライン初回訪問には対応しない(4の判断)。
- 検証: 障害注入E2E `tests/e2e/tests/resilience.spec.ts` が、接続失敗・503・無応答・鍵なし(実サーバー)を本番相当ビルドへ注入して画面を固定する。
