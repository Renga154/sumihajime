# ADR-016: API の入力を絞る — 住所の細目を受け取らず、本文・件数・生成に上限を置く

- Status: **Accepted — 2026-09-29**
- Date: 2026-09-29
- 関連: REQUIREMENTS §14.1(チェックリスト生成入力例)、§7.3 Step1、§13(ログ)、§11(RAG)、
  CLAUDE.md 原則6・7・8、`migrations/0006_chat_usage.sql`

## Context

セキュリティ監査で、API が「使わない入力」と「上限の無い入力」を受け付けていることが指摘された。

1. `destination.postalCode` / `destination.town`(町丁目)を任意項目として受け付けていた。
   REQUIREMENTS §14.1 の入力例がこの2項目を含むためだが、実際には **どの画面も送らず、
   ルール評価も API も一度も読まない**。受け取るだけの住所の細目は、将来ログや保存へ誤って
   流れる経路になる(原則6・7)。
2. `/api/chat` と `/api/checklists` の本文に大きさの上限が無く、Content-Type も見ていなかった。
   text/plain 等は CORS の「単純リクエスト」で、第三者サイトからプリフライト無しで送れるため、
   他サイト経由で利用者のブラウザに OpenAI の課金を起こさせることができた。
3. OpenAI 呼び出しに生成トークンの上限も、全体の1日上限も無かった(IP単位の制限は isolate 内の
   メモリだけで、IPを替えればすり抜けられる)。

## Decision

### 1. `destination` は `municipalityCode` だけを受け付ける(REQUIREMENTS §14.1 からの逸脱)

`destinationSchema` から `postalCode` / `town` を削除した。strictObject なので、送られた場合は
検証エラー(API は 422 `invalid_profile`)になる。

- **要件との関係**: §14.1 の例をそのまま送ると 422 になる。§14.1 は「初期案」の契約例で、§7.3 Step1 の
  「町丁目または郵便番号(必要な自治体のみ)」は MVP で使う場面が無い(ごみ収集地区は地区一覧から
  利用者が選ぶ方式で、住所から自動解決しない)。
- **影響**: 既存の画面・保存済みプロフィール(端末内)・E2E はこの2項目を持たないため影響なし。
  外部の利用者はいない(公開APIとして案内していない)。
- **戻し方**: 町丁目が必要になった時点(収集地区の自動解決など)で、用途・保存しないこと・
  ログに出さないことを決めてから、この ADR を更新して足す。
- **REQUIREMENTS の扱い**: 2026-09-29 にオーナーが承認し（「外す」）、§9.2 と §14.1 の例から
  `postalCode` / `town` を外して本 ADR を参照する形に更新した。

### 2. 入力の上限

- 本文: `/api/chat`・`/api/checklists` とも 8KB(hono `bodyLimit`。超過は 413)。
- Content-Type: 同2経路は `application/json` 以外を 415(プリフライトの要らない送信形を断つ)。
- 世帯: `memberCount` ≤ 20、`ageBands` ≤ 20 件(画面は最大6)。
- チャット: `question` ≤ 500 字(従来どおり)、`procedureId` / `category` ≤ 100 字。

### 3. 生成の費用に上限を置く

- 1回の生成は `max_tokens = 800`。
- 全体の1日上限 `CHAT_DAILY_LIMIT`(既定1500、日本時間の暦日)。D1 の `chat_usage` に
  `INSERT … ON CONFLICT(day) DO UPDATE SET count = count + 1 RETURNING count` で原子的に数える。
  - 数えるのは **OpenAI を呼ぶ直前**の要求だけ。必要書類の質問(検証済みデータ経路)・未対応自治体の
    案内・入力不備は課金を伴わないので数えず、上限到達後も必要書類の質問には答え続ける(原則8)。
  - 超過は 429。文面で「本日は停止中・チェックリストと公式リンクは使える」と伝える。
  - 計数そのものが失敗したら、チャットの生成だけを閉じる(503)。数えられないまま通すと上限が黙って
    消えるため。チェックリスト等はこの表に触れない。
  - 不正な値は既定値へ倒す(NaN にすると `count > NaN` が常に偽になり上限が消える)。`"0"` は当日の
    生成を止める緊急停止として有効。
- IP 単位の制限(10回/分)は残し、満タンに戻ったバケットを掃除してメモリの増加を止めた。

## Consequences

- **良い点**: 使わない住所情報を構造的に受け取らない。第三者サイト経由の課金・巨大本文による負荷を
  入口で断つ。1日の費用に上限がある。
- **代償**: §14.1 の例をそのまま送るクライアントは 422 になる(上記のとおり該当者はいない)。
- **代償**: 1日上限は全利用者で共有のため、1人が使い切ると他の人もその日は生成回答を受けられない
  (必要書類の質問・チェックリストは使える)。上限値は利用状況を見て `wrangler.jsonc` の vars で調整する。
- **運用**: `migrations/0006_chat_usage.sql` を本番・ミラー両方の D1 に適用してからデプロイすること。
  未適用のままだと計数が失敗し、チャットの生成は 503(閉じる側)になる。
