# ADR-018: 書籍に基づくセキュリティの強化 — 判断と、残したトレードオフ

- Status: **Accepted — 2026-10-03**
- Date: 2026-10-03
- 関連: ADR-011（セキュリティヘッダ）、ADR-016（API の入力を絞る）、ADR-017（独自ドメイン）、REQUIREMENTS §11.5・§11.6、
  CLAUDE.md 原則 2・4・6・7・8、[`docs/security/README.md`](../security/README.md)、`docs/security/findings.md`

## Context

2026-10-02 に、オーナーが書籍『Webアプリケーションセキュリティ入門』を基準に、アプリの強化を依頼した。
章の範囲で分けた 7 本の読み取り専用の監査（g1〜g7）を行い、高は 0 件、中が複数見つかった
（本番が平文 HTTP で 200 を返す、チャット以外の API に流量制限が無い、チャットが stale 判定を無視する、
RAG が承認状態を見ない、プロンプトの区切りの無害化が破れる、など）。
修正は 2026-10-03（JST）に本番とミラーへ反映した。一覧は `docs/security/findings.md`。

このサービスはログインも個人情報の保存も持たない。守るものは、公式根拠の正しさ、可用性、OpenAI の費用、
質問に混じる個人情報の扱いである。以下は、直し方が複数あり、トレードオフを選んだものの記録。

## Decision

**1. 流量制限は IP 単位。API は 300 回/60 秒、チャットは 10 回/60 秒。ループバックと送信元 IP の無い要求は数えない。**
Workers Rate Limiting のキーは `CF-Connecting-IP`（IPv6 は /64）。IP は利用者が偽れない値で、ログインが無いので他に鍵が無い。
当初 API は 120 回だったが、携帯回線や会場の共用 Wi-Fi では複数人が同じ IP になるため 300 に上げた（画面 1 枚は数回、
ごみ分別の検索は 300ms のデバウンスで 1 回なので、人の操作では届かない）。ループバックと IP 無しは、本番では起きず、
ローカルと E2E だけで、数えると並列の E2E が自分自身を 429 にするため除く。`/api/health` も外形監視のため除く。
数えるのは拠点（colo）単位で、バインディングの障害時は通す（fail-open）。これは追加の防御であり、閉じると Cloudflare 側の
一時障害が全面停止になるため。分散した攻撃には効かない。

**2. 公開 GET に 5 分のエッジキャッシュ、ごみ分別の品目一覧に isolate 内の 5 分キャッシュ。古さは許容する。**
流量制限だけでは、変化する検索語で D1 の 1 日の読み取り枠（Workers Free）を減らされる。同じ応答を使い回すことで
D1 の読み取りを減らす。代償は、データ更新が最大 5 分遅れて見えること。更新は人の承認を経る日次〜週次の頻度なので許容した。
エッジキャッシュは正典ホストだけ（ミラーは対象外）。保存するのは本文と Content-Type だけで、ヘッダは保存しない。

**3. POST の Origin・Sec-Fetch-Site を検査する。ヘッダの無いクライアントは通す。**
別サイトのページから費用のかかる POST を打たせない（踏み台の防止）。Cookie は使わないので、CSRF の被害そのものは小さい。
評価スクリプトや curl はヘッダを付けないため、「ヘッダがあり、かつ同一オリジンでない」ときだけ 403 にする。
ヘッダを偽装できる非ブラウザのクライアントには効かない（そこは流量制限の担当）。

**4. チャットは stale な根拠を、保留せず警告つきで答える（REQUIREMENTS §11.5）。**
巡回が変更を検知した根拠は、引用に検知日と種別を付け、確度を low に下げ、画面で「要確認」と出す。保留にしなかったのは、
検知が「公式ページが変わった」であり「内容が誤り」ではないため。保留すると多くの質問に答えられなくなる。
利用者が確認できるように公式リンクを必ず添える。代償は、古い情報が警告つきで表示されること。

**5. 回答の URL・電話・メールを、選択自治体の承認済みソースに限る。**
生成された回答の URL は、選択自治体に適用される承認済みソースのホスト、または抜粋にそのまま出ている URL に限る。
電話・メールは抜粋に無ければ保留する。以前は任意の `.lg.jp` / `.go.jp` を通したため、別の区のページが出得た（原則 4）。
LLM の出力は信用せず、出てきた連絡先を根拠と機械的に照合する。代償は、正しい URL を保留する誤検知が出得ること。
その場合は回答を保留して公式リンクを案内する（安全側）。

**6. 個人情報の検出を、Web と API の両方で行う。**
電話・メール・12 桁の個人番号を含む質問は、API が外部呼び出しと利用回数の加算より前に 422 で止める。画面も同じ検出器で
送信前に止める。画面だけでは迂回できる。API だけでは、利用者が書いた直後に気づけない。検出は誤検知があり得るので、
文面に「番号を書かずに質問してほしい」と次の行動を示す。検出した値はログにも応答にも出さない（原則 7）。

**7. Workers の invocation logs を止める。**
新しい Worker は、各要求の URL・ヘッダを自動で記録する。プライバシーポリシーは「許可リストの項目だけ記録し、IP は記録しない」と
約束しているため、自動記録を止め、`src/log.ts` の行だけを残す。代償は、障害調査で要求の詳細が見えないこと。
必要なら、個人情報を含まない項目を許可リストに足す。設定を省くと既定に戻るため、両環境に明示して固定する。

**8. HSTS は付けるが preload はしない。**
1 年・サブドメイン込みで付ける。preload は、全サブドメインを恒久的に https 専用にする約束で、取り消しに数か月かかる。
ドメインを取得したばかりで、サブドメインの使い方（メール・検証用）が決まっていない。決まったら再検討する。
初回アクセスの格下げは、Worker の 301 と Always Use HTTPS が受け持つ。

**9. Turnstile は見送る（2026-10-02 オーナー判断）。**
チャットの全員共有の 1 日上限を 1 人で使い切れる問題（SEC-03）は、IP 単位の制限（1）で緩和した。Turnstile は
利用者に手間をかけ、アクセシビリティと可用性の面でも負担になる。いまの利用規模では、IP 制限と上限、利用額の通知（SEC-42）で足りる
と判断した。濫用が実際に見えたら導入する。

**10. `xlsx` 0.18.5 は更新せず、緩和する。**
既知の脆弱性（プロトタイプ汚染、ReDoS）は、細工したファイルを解析したときだけ発火する。解析は、台帳のハッシュと
一致した承認済みファイルだけにし、行・列の範囲を制限し、数式・HTML・VBA の解析を切った。パッケージの入れ替えは
サプライチェーンの判断なので、人が決める。残るリスクは、承認済みのファイル自体が細工されている場合。

**11. チャットのモデルを `gpt-4o-mini-2024-07-18` に固定する。**
別名のままでは、中身が知らないうちに変わり、回答の質と評価の再現性が崩れる。それまでの別名と同じスナップショットを日付つきで固定した。
代償は、OpenAI が古い版を終了したときに自分で更新する必要があること。更新はテストと評価を再実行して行う。
評価レポートにモデル名を残す仕組みは入れたが、API の応答がまだモデル名を返さない（SEC-33）。

**12. security.txt の Policy は `SECURITY.md` を指す。**
窓口は、メールを公開しない方針（2026-09-22）に沿って、画面の問い合わせフォームのままにする。Policy に `SECURITY.md` を置き、
テストの範囲（本番で攻撃的な操作をしない、負荷試験をしない）を報告者に伝える。Expires は 2027-10-01 で、
過ぎるとテストが落ちるようにして、放置を防ぐ。

## Consequences

- 利用者から見える変化: 短時間に連打すると 429（`Retry-After` つき）、個人情報の疑いがある質問は送信前に止まる、
  stale な根拠は「要確認」と出る、データの更新が最大 5 分遅れて見える。
- 運用の変化: invocation logs が無いので、障害の調査は許可リストのログと外形監視が頼り。RAG の索引は
  非表示要素の除去に合わせて両環境で再構築した（2026-10-03、1,950 チャンク）。
- 残した課題は `docs/security/findings.md` の「未対応」と `docs/ROADMAP.md` にある。とくに SEC-40（OpenAI キーの分離と予算）、
  SEC-41（旧ホストの API）、SEC-42（通知とインシデント手順）。
- 流量制限と Origin 検査は、分散した攻撃や、ヘッダを偽装する非ブラウザには効かない。費用の総量は、1 日上限と
  OpenAI 側の予算（未設定）で守る前提。

### 見直しの条件

- 濫用が実際に観測された（429 の急増、1 日上限の頻繁な到達、OpenAI の利用額の急増）: Turnstile、またはキー単位の制限を検討する。
- 共用 IP で正当な利用者が 429 になる報告が出た: 300 回/60 秒を見直す。
- サブドメインの使い方が決まった: HSTS preload を再検討する。
- 更新が遅れて困る報告が出た: キャッシュの TTL（300 秒）を短くする。
- `xlsx` の代替が見つかった、または上流が修正した: 入れ替える。
- OpenAI が固定したモデルの版を終了する: 評価を再実行して版を上げる。
