## P0 — 公開前に必ず直す

### P0-1. 存在しないURLで、英語の開発者向けエラー画面が全画面表示される

**再現手順**

1. ブラウザで `https://app.sumihajime.workers.dev/typo-url` を開く（`/checklist2` など任意の未定義パスで可）。

**観測結果**

```
Unexpected Application Error!
404 Not Found

💿 Hey developer 👋

You can provide a way better UX than this when your app throws errors by providing your own ErrorBoundary or errorElement prop on your route.
```

ヘッダー・ナビ・フッターがすべて消え、日本語も無く、トップに戻る導線もない。ブラウザバック以外に復帰手段がない。

**なぜ問題か**

- サービスデザイン: 都民向け公共情報サービスで、英語の開発者向け文言が一般利用者に露出する。「行政っぽい信頼感」を売りにしているプロダクトの信頼を一撃で壊す。
- 審査への直撃: 審査委員が資料のURLを手入力する／古いリンクを踏む／`/coverage` 以外の旧パスを試す、いずれでもこの画面に到達しうる。3分審査で最初に見る画面がこれになる可能性がある。
- 技術力: `errorElement` 未設定は「完成度」の減点として明示的に読み取れる。

**原因**

`apps/web/src/main.tsx` の `createBrowserRouter` に catch-all（`path: '*'`）も `errorElement` も無い。加えてルート要素にErrorBoundaryが無いため、**任意の描画時例外でも同じ画面になる**。実際、点検中の再デプロイのタイミングで旧アセットが404になり、`/checklist` が完全な白画面（`#root` が空）になる事象も観測した（P2-9参照）。

**修正の方向性と規模**

`main.tsx` に `{ path: '*', element: <NotFoundPage /> }` と、`element: <Layout />` へ `errorElement: <AppErrorPage />` を追加。NotFound/AppErrorは既存の `ErrorMessage` を流用した20〜30行程度のページで足りる。**規模: 小（1〜2時間）**。

**修正しない選択の妥当性**: 妥当でない。コストが小さく、露出の期待値が大きい。

### P0-2. 窓口一覧の地図に背景地図が1枚も表示されない（マーカーだけが無地の上に浮く）

**再現手順**

1. トップで **世田谷区**（座標データを持つ11区のいずれか。大田・江東・中野・杉並・荒川・練馬・新宿・墨田・渋谷でも可）の「この自治体で始める」を押す。
2. ヘッダーの「窓口一覧」を開く。

**観測結果**

46個のピンが**無地の薄いグレー**の上に並ぶ。地理院タイルの地図画像は1枚も表示されない。にもかかわらず地図右下には「出典: 地理院タイル」の帰属表示だけが常時出ている。DevToolsのネットワークに `cyberjapandata.gsi.go.jp` へのリクエストは**1件も出ない**。

**原因（特定済み）**

MapLibre GL のWeb Worker用モジュールが本番に存在しない。

```
$ curl -o /dev/null -w "%{http_code} %{content_type}\n" \
    https://app.sumihajime.workers.dev/assets/maplibre-gl-worker.mjs
200 text/html          ← JSではなくSPAのindex.htmlが返る
```

ブラウザコンソールにも対応するエラーが出る:

```
Failed to load module script: The server responded with a non-JavaScript MIME type of "text/html".
```

ローカルの `apps/web/dist/assets/` にも `maplibre-gl-worker.mjs` は生成されていない（`index-*.js` / `maplibre-gl-*.js` / フォントのみ）。**Viteのビルドでmaplibreのworkerチャンクが出力されていない**のが根本原因。ワーカーはラスタタイルのデコードに必須なので、タイルレイヤだけが無音で死に、DOMマーカー（`.maplibregl-marker`）は描画される。`FacilityMap` の `failed` フォールバックは `map` の初期化例外だけを見ているため、この失敗パターンを捕捉できない。

**なぜ問題か**

- **データ活用（審査基準1）への直撃**: 「複数のオープンデータを統合し、直感的に可視化する」が過去2年の最優秀賞の型。本作でその型に一番近いのが施設地図で、それが壊れている。
- **正確性**: タイルが出ていないのに「出典: 地理院タイル」だけ表示するのは、利用規約上の出典明示としても実態と合わない。
- **技術力**: デプロイ資産の欠落＝完成度の減点。

**修正の方向性と規模**

1. まず `pnpm --filter web build` 後に `dist/assets/maplibre-gl-worker.mjs` が出るかを確認する。出ないなら Vite の `worker: { format: 'es' }` 指定、または maplibre の `maplibregl.setWorkerUrl()` / `workerClass` でバンドル済みワーカーを明示注入する。
2. あわせて `FacilityMap` に「タイル読込失敗」の検出を足す（`map.on('error')` で `sourcedata`/tile系エラーを拾い、失敗時は地図領域を畳んで一覧のみにする）。帰属表示も地図が出ていないときは出さない。
3. E2Eに「タイルリクエストが1件以上発生する」アサーションを1本追加すると再発を防げる。

**規模: 中（半日〜1日）**。原因は特定済みなので調査コストは不要。

**修正しない選択の妥当性**: 「地図をやめて一覧＋Googleマップリンクに一本化する」なら妥当。現状でも `地図で見る` の外部リンクは全施設で機能している。ただし**壊れた地図を出したまま**は最悪の選択肢なので、直すか消すかの二択にすべき。

### P0-3. AIチャットが江戸川区で「転入届の持ち物」を誤って回答し、確度「高」を付ける

**再現手順**

1. トップで **江戸川区** を選ぶ → 引越し日と転入元を入力 → チェックリストを作成。
2. ページ下部の「AIに質問する（ベータ）」に、**プレースホルダに書かれている例文そのもの**「転入届に必要な持ち物は？」を入力して送信。

API直叩きでも同じ:

```
$ curl -s -X POST https://app.sumihajime.workers.dev/api/chat \
   -H 'content-type: application/json' \
   -d '{"municipalityCode":"13123","question":"転入届に必要な持ち物は？"}'
```

**観測結果（再現性あり。表現違いの2質問・API直叩きでも同一の主張）**

> 確度: 高
> ①転入届に必要な持ち物は、転入される方全員のマイナンバーカードです。
> ②手続き時に、住民基本台帳用暗証番号（数字4桁）を入力する必要があります。…

同じアプリの**手続き詳細ページ**（同一出典）は正しく以下を出している:

- 必須: 窓口にお越しになる方の本人確認できるもの
- 場合により必要: 転出証明書（前住所地の市区町村で発行を受けたもの）
- 場合により必要: 転入される方全員分のマイナンバーカード**（お持ちの方）**

つまりチャットは、**必須の本人確認書類と転出証明書を落とし、「お持ちの方」限定の任意項目を唯一の必須物として断定**している。

**他区との比較（同じ質問をAPIで実行）**: 世田谷区・千代田区・足立区・豊島区はいずれも転出証明書＋本人確認書類を含む妥当な回答。**江戸川区が外れ値**。系統的な欠陥ではなく特定区の退行。

**なぜ問題か**

- 実害: マイナンバーカードだけ持って窓口に行くと手続きできない。転入届は住基法上14日以内・過料ありの手続きで、出直しのコストが実際に発生する。
- CLAUDE.md原則3（根拠がない場合は推測しない）・原則1の趣旨に反する。「確度: 高」ラベルが誤りを補強している。
- 審査基準「技術力」「サービスデザイン」双方に響く。審査委員は必ずプレースホルダの例文を試す。

**修正の方向性と規模**

- 即応: RAG評価セット（`docs/research/rag-eval-*.md`）に「23区×転入届の持ち物」を必須ケースとして追加し、`requiredDocuments` の `status=required` 項目が回答に含まれることを機械検証する。
- 根本: 手続きに構造化された `requiredDocuments` が既に存在するのだから、**「持ち物」意図の質問はLLM生成ではなく構造化データを直接返す**（LLMは補足のみ）ルートを用意するのが最も安全。決定論的で、原則1「該当判定をLLMへ任せない」とも整合する。
- 併せて、confidence が high のとき「詳細ページの必要書類一覧も必ず確認してください」への導線を回答直下に常設する。

**規模: 中（1〜2日）**。評価ケース追加だけなら半日。

**修正しない選択の妥当性**: 妥当でない。誤案内は本プロダクトの存在意義を否定する。

### P1-1. 透明性ページが「AIチャット相談 未対応」と書いている区で、AIチャットが動いて回答する

**再現手順**

1. `/about-data` を開き、「対応している自治体と内容」から **江戸川区** を展開する。
   → カテゴリ表に「**AIチャット相談: 未対応**」と表示される。
2. トップから江戸川区を選び、チェックリストを作る。
   → ページ下部にAIチャットパネルが**表示され**、江戸川区の出典カード付きで**回答する**（P0-3参照）。

**範囲（APIで機械確認）**

```
$ curl -s https://app.sumihajime.workers.dev/api/municipalities | \
  # coverage.rag != 'verified' の対応区を抽出
16件: 中央・港・文京・台東・墨田・目黒・渋谷・中野・豊島・北・荒川・板橋・練馬・足立・葛飾・江戸川
```

一方、リポジトリの `docs/data-sources/coverage.csv` は**23区すべて `rag=verified`**。つまり**本番D1の `coverage` テーブルがリポジトリの正データから乖離**している（publishが未反映）。また `GET /api/chat/availability` は `municipality` パラメータを受け取っても無視し、グローバルの `RAG_ENABLED` だけを返すため、UIはcoverageと無関係にパネルを出す。

**なぜ問題か**

- 透明性ページは本サービス最大の差別化資産で、審査委員が「データ活用」「サービスデザイン」を確認しに来る場所。そこが**実装と矛盾**しているのは、原則9（未対応を対応済みに見せない）の裏返しで、同じくらい信用を損なう。
- 「AIチャットは7区のみ」と読んだ審査委員は、23区で動くという実力を過小評価する。損をしているのは本プロダクト側。

**修正の方向性と規模**

1. `coverage.csv` を本番D1へ再publishする（運用手順の実行のみ。**規模: 極小**）。
2. 恒久対策として、`/api/chat/availability` に `municipality` を渡し、coverage が `unavailable` の区ではパネルを出さない（またはUIとcoverageの一致をE2Eで検証する）。**規模: 小**。
3. 「本番D1 と `docs/data-sources/coverage.csv` の差分がゼロであること」をCIまたはデプロイ後スモークで機械検証する。**規模: 小**。

**修正しない選択の妥当性**: 妥当でない。再publishだけで直る上、放置すると提出資料の記述とも矛盾する。

### P1-2. 入力画面（/wizard）に、選択中の自治体が一度も表示されない

**再現手順**

1. トップで任意の区（例: 世田谷区）の「この自治体で始める」を押す。
2. 遷移先 `/wizard` の全文を読む。

**観測結果**

見出しは「条件を入力する」。ステップ1〜3のどこにも「世田谷区」の文字がない（`document.body.innerText` に区名が含まれないことを確認）。自治体を選び直す導線もない（ヘッダーの「ホーム」から戻るしかない）。区名が初めて出るのは、入力を終えて `/checklist` に到達した後。

**なぜ問題か**

- 入力を全部終えてからでないと区の誤りに気づけない＝手戻りが最大化する動線。

**修正の方向性と規模**

`/checklist` に既にある自治体チップ（`📍 世田谷区`）をウィザードのヘッダーへ再利用し、隣に「自治体を変える」リンクを置く。**規模: 小（1〜2時間）**。

**修正しない選択の妥当性**: 妥当でない。既存コンポーネントの再配置だけで、効果が大きい。

### P1-3. ページ遷移でスクロール位置がリセットされず、ブラウザバックでも復元されない

**再現手順（遷移時）**

1. トップを下までスクロールし、リストの下の方の区（例: 江戸川区）の「この自治体で始める」を押す。
2. 遷移直後の画面を見る。

**観測結果**: `/wizard` の**最下部**に着地する（`window.scrollY` はページ高の上限までクランプされる。実測 `scrollY=245.5, scrollHeight=965, innerHeight=720`）。画面には「転入元区分」のラジオと最下部のボタンだけが見え、**必須の「引越し日」入力と見出しが画面外の上**にある。何を求められているか分からない。

**再現手順（バック時）**

1. トップを下までスクロールして区を選ぶ → `/wizard`。
2. ブラウザの戻るを押す。

**観測結果**: `/` に戻るが `scrollY=0`。62件・約3500pxのリストの先頭に放り出され、さっき見ていた場所を探し直すことになる。

**なぜ問題か**

- 主要導線の入口で必ず起きる。モバイルではリストが長い分さらに深刻。
- 「戻れない・迷う」の典型で、サービスデザインの評価に直結する。

**原因**: `createBrowserRouter` を使っているが `<ScrollRestoration />` を配置していない。

**修正の方向性と規模**

`Layout` に `<ScrollRestoration />` を1行追加（react-router-dom 標準）。バック時の位置復元と遷移時のトップ復帰が同時に解決する。**規模: 極小（15分＋テスト）**。

**修正しない選択の妥当性**: 妥当でない。

### P1-4. 画面遷移でフォーカスが body に落ち、`<title>` も全ページ同一

**再現手順（フォーカス）**

1. キーボードのみでトップを操作し、Tabで区の「この自治体で始める」まで移動してEnter。
2. そのままTabを1回押す。

**観測結果**: 遷移後の `document.activeElement` は `<body>`（実測）。Tabはページ先頭の「本文へスキップ」に戻る。**キーボード利用者は毎回ページ先頭から辿り直す**。スクリーンリーダーにはページが変わったこと自体が通知されない（route announcer が無い）。

**再現手順（タイトル）**

1. `/`, `/wizard`, `/checklist`, `/facilities`, `/waste`, `/about-data`, 未定義URL を順に開き、ブラウザのタブ名を見る。

**観測結果**: すべて `スミハジメ 〜東京の新生活ToDo〜`。履歴・ブックマーク・タブ切替・スクリーンリーダーのページ読み上げのいずれでも区別できない。

**なぜ問題か**

- WCAG 2.4.2（Page Titled）は各ページを識別できるタイトルを求める。SPAでは `document.title` の更新が必要。
- キーボード／スクリーンリーダーでの完走可能性に直結。フォーカスリング自体はDADS準拠で非常に良く作られているだけに、遷移時の扱いだけが穴になっている。

**修正の方向性と規模**

- ルート変更時に `<h1>` へ `tabIndex={-1}` でフォーカスを移す小さなフック（`useRouteFocus`）を `Layout` に追加。
- 各ページで `document.title = '<ページ名> | スミハジメ'` を設定（`useDocumentTitle` フック1本＋各ページ1行）。
- 併せて `aria-live="polite"` の視覚非表示ノードにページ名を流すと読み上げ通知になる。

**規模: 小（半日）**。

**修正しない選択の妥当性**: タイトルだけ先に直して、フォーカス移動は後回しにするのは妥当な段階分割。ただし両方とも小さい。

### P1-5. 期限を過ぎていることを一切表示しない／日付入力に上下限がない

**再現手順（過去日の現実的ケース）**

1. 江戸川区を選ぶ。引越し日に **2026-06-01**（点検日の約2か月前）、転入元「東京都外」を入力してチェックリストを作成。

**観測結果**: 「転入後すぐ」に「転入届」が **優先度: 至急 / 期限: 2026年6月15日** と表示される。**期限を54日過ぎているという表示・警告・次にとるべき行動の案内が一切ない**（本文中に「過ぎ」「期限切れ」「超過」に相当する語が存在しないことを確認）。`.ics` にも過去日の予定として書き出される。

**再現手順（極端値）**

1. 同じ画面で引越し日に **1900-01-01** を入力する。

**観測結果**: そのまま受理され、「期限: **1900年1月15日**」と表示される。`input[type=date]` に `min`/`max` 属性はなく（実測 `min=""`, `max=""`）、アプリ側の検証もない。

**なぜ問題か**

**修正**: ヒーロー内に「自治体を選ぶ」ボタン（`#municipality-picker` へのアンカー）を1つ置く。または「ご利用の前に」を折りたたみにして既定は要約1行にする。**規模: 極小〜小**。

### P2-6. 選択中の自治体がトップで分からない

**再現手順**: 区を選んだあと、ヘッダーの「ホーム」で戻る。

**観測結果**: 23枚のカードはすべて「対応済み／この自治体で始める」で、いま選んでいる区に印がない（「選択中」に相当する表示なし）。

**修正**: 選択中カードにバッジと `aria-current` を付ける。**規模: 極小**。

### P2-7. 進捗の「%」記号のコントラストが 2.63:1

**再現手順**: `/checklist` の進捗カード「0%」の「%」部分の色を測る。

**観測結果**: `oklch(0.704 0.04 256.788)`（slate-400相当）／白背景、14px semibold で **CR 2.63:1**（WCAG 1.4.3 の 4.5:1 未満）。

**補足**: 同じ手法でトップ・チェックリスト全要素を機械測定したところ、**指摘はこの1件のみ**。ブランドカラーやフォーカスリングを含め、コントラスト設計は全体として非常に良い。

**修正**: `text-slate-400` → `text-slate-500` 以上に。**規模: 極小**。

**修正しない選択の妥当性**: 「%」は隣の数値と併記され、単独では意味を持たない装飾的単位とも解せる。**優先度を下げるのは妥当**。

### P2-8. ハッシュ付き不変アセットに `max-age=0, must-revalidate` が付いている

**再現手順**

```
$ curl -sI https://app.sumihajime.workers.dev/assets/noto-sans-jp-japanese-400-normal-Cy9Yahyj.woff2 | grep -i cache
cache-control: public, max-age=0, must-revalidate
```

**なぜ問題か**: ファイル名にハッシュが入っているのに毎回再検証する。ページ遷移のたびにフォント3本＋JS/CSSで6〜9往復の条件付きGETが走る（304なので帯域は消費しないが、モバイル回線ではRTTがそのまま体感遅延になる）。

**修正**: Workers Assets の設定で `/assets/*` に `cache-control: public, max-age=31536000, immutable` を付与。`index.html` は現状の `max-age=0` のままでよい。**規模: 極小**。

### P2-9. デプロイ中に旧アセットが404となり、開いていたページが白画面になる

**再現手順（機会依存）**: アプリを開いた状態で再デプロイが走ると発生。点検中に実際に遭遇した。

**観測結果**: `/checklist` が完全な白画面（`#root` の中身が空）。コンソールに `Failed to load resource: 404` ×3 と `Failed to load module script: ... MIME type "text/html"`。ヘッダーもフッターも出ないため、利用者は「サービスが落ちた」と判断する。

**なぜ問題か**: SPA + ハッシュ付きアセット + 未定義アセットへのHTMLフォールバックの組み合わせで、デプロイのたびに既存セッションが壊れうる。P0-1のErrorBoundary不在が症状を最悪化させている。

**修正**: (a) ErrorBoundary を入れて「新しいバージョンがあります。再読込してください」に落とす、(b) `/assets/*` の未知パスは200のHTMLではなく404を返す、(c) 直近1〜2世代のアセットを残す。**規模: 小**。P0-1の修正で(a)は自動的に片付く。

### アイデア力とソーシャルインパクトへの提言（実装ではなく見せ方の問題）

いずれもプロダクトの実力は既にあるので、**追加開発ではなく1画面の追記**で改善できる。

1. **トップに「このサービスの約束」を3行で置く**（ヒーロー直下、免責カードの前）。例:
   「① 表示するすべての手続きに、公式ページの根拠と最終確認日を付けています（332件の公式ソース）。② 根拠が無いことは『要確認』と書き、推測しません。③ 未対応の自治体・カテゴリを対応済みには見せません。」
   → これだけで「アイデア力」と「データ活用」の両方が3分審査の視界に入る。**規模: 極小**。
2. **数字を1つだけ出す**。「23区 / 332件の公式ソース / 最終確認 2026年8月7日」をトップのヒーロー内にバッジで置く。透明性ページに既にある値をそのまま持ってくるだけ。**規模: 極小**。
3. **ソーシャルインパクトは「対象人数×削減時間」の1文**をトップかフッター上に置く。根拠として使える公表統計（住民基本台帳人口移動報告の東京都転入者数など）を出典付きで示せば、本作の「根拠を付ける」姿勢とも一貫する。**規模: 小**（出典audit込みで半日）。
4. **`og:image` / `og:title` / `og:description` を入れる**。現状メタタグは `description` のみで、OGP系が一切ない（実測）。提出フォームやSNSにURLを貼っても素っ気ないリンクにしかならない。**規模: 極小**。

## 良かった点（減点の裏返しにしないための記録）

審査委員視点で明確に加点できると判断した点。修正提案の際に壊さないよう記録しておく。

- **透明性ページの完成度**。332件の出典台帳、ライセンス・帰属・最終確認日、鮮度の集計、そして「オープンデータ品質レポート」（新宿区CSVの施設欠落、世田谷区CSVの列入れ替わり）まで公開している。この最後の一つは、単なる利用者ではなく**オープンデータのエコシステムへ貢献する立場**を示していて、他作品と明確に差がつく資産。もっと前面に出すべき。
- **未対応の誠実な扱い**。未対応区・未対応カテゴリを一貫して「未対応」と表示し、公式サイトへ逃がす。原則9が実際に守られている。
- **RAGの保留動作**。「世田谷区の粗大ごみの申し込み方法」を江戸川区の文脈で聞くと、推測せず「確認できませんでした（公式の根拠が見つかりませんでした）」と返し、公式ページへ誘導する。自治体スコープの逸脱も観測されなかった。
- **フォーカスリングと見出し構造**。DADS流の黒アウトライン＋黄リングは明暗どちらでも視認でき、`h1→h2→h3` の階層も各ページで崩れていない。ランドマーク（banner/nav/main/contentinfo）とスキップリンクも揃っている。フォームは `fieldset`/`legend` を正しく使っている。
- **コントラスト設計**。全要素を機械測定して不足は1件のみ（P2-7）。
- **外部リンク衛生**。すべて `rel="noreferrer noopener"` かつ「（別タブで開きます）」の視覚非表示テキスト付き。
- **プライバシー実装**。`.ics` はクライアント生成、チャットは質問文・回答本文をログに残さない設計、収集する個人情報がゼロ。
